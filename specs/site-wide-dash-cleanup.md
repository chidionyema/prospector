# Site-wide dash cleanup (mumchimp.com)

**Status:** proposed
**Scope:** all `*.tsx` source files and static JSON data under `store_platform/src/Store.Web/src/`

---

## Problem

The kill-log page on `mumchimp.com/kill-log` rendered 180 em/en-dashes across 60 entries
(3.4 per 1,000 chars) — the most universally recognised AI writing signature. The
`tools/make_kill_log.py` fix landed first, but a sweep of the rest of the storefront
found the same tell **across 64 source files**: 311 em/en-dashes in hand-written JSX
prose, comment blocks, and JSX attribute values. The pattern is the same everywhere:
`Brand — Description`, `…is already served by incumbents — National Testing, UKAS ISO
17025…`, `Get instant access — £49`. The `/how-it-works` page reproduced the same
problem because the kill-log JSON it pulls from was also dash-heavy.

The kill-log tool change addressed the kill-log page. This spec covers the rest of the
storefront.

## Fix

Three layers, all cosmetic post-processing:

1. **Shared helper** — `store_platform/src/Store.Web/src/lib/text.ts` exposes `nodash()`
   written in TypeScript. The substitution rule is byte-for-byte identical to the Python
   `nodash()` in `tools/make_kill_log.py`:

   - `—` (em-dash) → `, `
   - `–` (en-dash) → `, `
   - ` - ` (hyphen surrounded by whitespace) → `, `
   - Multiple internal whitespace → single space
   - Space before punctuation → dropped

2. **Source-level rewrite** — every remaining em-dash in every `.tsx` source file is
   replaced with `, ` (or `: ` where the em-dash introduces a list, `to` for ranges —
   handled by the helper). The replacement is mechanical because the existing copy was
   always dash-as-separator, never dash-as-meaning. The post-build rendered HTML is
   asserted dash-free by a new contract test.

3. **Render-side safety net** — JSX components that render dynamic text from JSON
   already feed through the kill-log approach (which normalises at the data layer). The
   `kill-log.json` regenerated by `tools/make_kill_log.py` is already clean; the sample
   report is already clean. The remaining dynamic surfaces — `pages/pack/[id].tsx`,
   `pages/ideas/index.tsx`, `pages/ideas/[slug].tsx` — render from the live API
   (`store/dossiers/*.json`) and likewise need `nodash()` at the render boundary.

## Acceptance

- `tests/unit/test_kill_log_dash_normalization.py` remains green (kill-log PR).
- `dashFree.test.ts` is green: every `.tsx` source file under `pages/` and `components/`
  has zero em-dashes and zero en-dashes.
- Full pytest suite remains green.
- The static `data/kill-log.json` has zero em/en-dashes (re-baked).
- The TypeScript build (`npm run build`) emits clean HTML — no em-dashes in any rendered
  page.

---

## Why this is not a moat change

None of the engine's verdicts, the candidate generator, or the verifier brain is
touched. The fix is purely cosmetic at the publish boundary. The kill-log data layer
change is already live; this sweep extends the same pattern to the rest of the
storefront.

---

## Out of scope

- The candidate generator prompt and the verdict prompt are not changed. Future content
  will still be written with em-dashes by the model; the post-processor catches them at
  publish time. Tightening the prompts would be a separate, larger change.
- The cloud-storage URL endpoints (`store_platform/src/Store.Web/src/__tests__/`,
  `store/scheduler/audit/`, `store/control_center/`) are not touched.
