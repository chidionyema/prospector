Runner Rot, tells you which self-hosted CI boxes drift.

A weekly data feed telling platform and DevOps leads inside UK software firms exactly which of their self-hosted GitHub Actions runner images have fallen behind GitHub's own hosted image, and what will break first.

Start with the plain version. GitHub publishes, in the open, the full contents of every hosted runner image it ships — every tool, every version, every change, in the actions/runner-images repository on GitHub, updated continuously. Firms that run their own build machines instead of GitHub's hosted ones pinned those images once and then quietly stopped. Two years later their runner has Node 18, a stale .NET SDK and an OpenSSL that fails a customer's security questionnaire, and nobody knows until a build breaks or an auditor asks.

This is a paid weekly intelligence product, not a tool anyone installs. The buyer sends one read-only output — the tool inventory their runner already prints at the start of every job — and gets back a ranked list. Which packages are behind. Which of those carry a published security advisory. Which GitHub actions in their workflows have already announced they will stop supporting the runtime they are pinned to. And the one that costs money: which upcoming GitHub deprecation dates land inside their next quarter.

The angle here is the one that grows as the platform gets stricter. GitHub is the party imposing the deadlines, and GitHub cannot take the buyer's side. Its own deprecation notices are written to protect GitHub's rollout, not to tell one specific firm in Leeds that their particular runner fleet has eleven things that will fail on a named date. GitHub will never say "you personally are exposed here" — that is commercially and legally not a thing a platform does for a customer's own infrastructure.

The compounding part is the operator's own archive. Every week the operator snapshots the public hosted-image manifests and stores them. Within a year that is a private time series nobody else holds: how long each tool actually lagged, which deprecations slipped, which announced dates moved. That history is what turns "you are behind" into "this class of change historically gets enforced six weeks after announcement, so book the work now." GitHub does not publish that history in a comparable form, and a firm starting today cannot backfill it.

One person runs this. A scheduled script pulls the public manifests and advisory feeds. The buyer's inventory arrives by email. The write-up is a page. Distribution is free and owned: publish the aggregate lag chart publicly each month, which is exactly the sort of thing platform engineers circulate.

Platform engineering leads and DevOps managers at UK software companies with roughly 20 to 300 engineers who run their own build machines — typically because of cost or because customer contracts forbid shared infrastructure. They already hold tooling budget and they are the person who gets asked, during a customer security review or an ISO 27001 surveillance visit, to prove the build environment is current. Price it around £180 a month per fleet.

GitHub has been retiring older hosted runner images and older versions of its own actions on published timetables, and each retirement forces work on anyone who pinned to the old thing. UK software firms selling into enterprise and public sector buyers now face supply-chain questions in nearly every procurement pack, and the build environment is squarely inside that scope. Meanwhile self-hosting build machines got popular as a way to cut cloud spend, so the number of stale, unowned runner fleets has grown fast.
