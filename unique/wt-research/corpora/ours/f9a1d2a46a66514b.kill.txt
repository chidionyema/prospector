BuildBreak Index, tells CI vendors whose runners just broke.

A weekly data feed for platform engineering leads that shows which hosted CI runner images, GPU instance types and package registries silently broke builds this week, and which exact image tag fixed it.

This is a data business, not a tool. We continuously run a fleet of small, deliberately boring reference builds — a Rails app, a PyTorch training job, a React Native app, a Go service, a CUDA kernel — on every major hosted runner in the United States: GitHub Actions ubuntu-latest and macos-latest, CircleCI machine images, AWS CodeBuild, Google Cloud Build, and GPU instance families in us-east-1 and us-west-2. Each build runs on a schedule, from a clean cache, pinned and unpinned. We record what broke, when, and on which image tag.

The output is a subscription feed. It says things like: macos-15 runner image bumped Xcode on this date, breaking React Native builds that pinned an older CocoaPods; the fix is this tag. Or: this GPU instance type in this region started failing this CUDA build on this date. The buyer gets an email, a Slack alert and an API endpoint.

The person who pays is the platform engineering lead or developer productivity manager inside a 50 to 500 person software company. That is an operations manager by another name. They own a cross-system mess — CI, cloud, package registries — and they get paged when the build queue backs up. Their daily friction is spending a morning proving that a build failure came from a vendor's image change, not from their own team's commit.

The angle here is inversion. The value grows exactly as the platforms get more aggressive about rolling images forward. GitHub publishes runner image release notes and deprecation notices in the actions/runner-images repository, and CircleCI publishes image deprecation schedules. But a platform structurally cannot publish this: it cannot run adversarial evidence against itself, cannot say which of its own image bumps broke paying customers, and cannot compare its breakage rate against a rival's. Only an outside party with no side can. That is the whole business.

The asset compounds. After two years we hold a longitudinal record of every hosted runner change and its real-world blast radius, built from builds we own. Nobody can retroactively acquire that. A competitor starting later starts with an empty history, and history is the product — buyers ask 'has this image family broken us before?', which is a question only accumulated observations answer.
