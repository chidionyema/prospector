Deprecation Desk, we rewrite the code a vendor just broke.

When a software vendor kills an API your agency built on, we rewrite every affected client project for a fixed fee per project, within the vendor's own deadline.

This is a fixed-fee rewrite service for small digital agencies in the UK that build and maintain client websites and apps on other people's platforms.

Here is the daily pain. An agency owner with 8 developers maintains 40 client sites built on Shopify, HubSpot, Stripe, Xero, Meta's marketing tools and the Microsoft Graph. Each of those platforms retires old versions of its programming interfaces on a published schedule. Shopify releases a new Admin API version every quarter and supports each version for 12 months, so anything built more than a year ago stops working on a date that is already printed on Shopify's own developer site. Stripe, Xero, Meta and Google Ads publish similar retirement calendars. The agency did not choose these dates and cannot bill a client for them, because the client's answer is always the same: the site worked yesterday, why am I paying for it to keep working.

So the work gets done at night, unbilled, by the one developer who remembers that project. That is the friction we start from, rather than from any idea about tooling.

We rebuilt this from the raw pain instead of the usual fix. The usual fix is a monitoring dashboard that tells the agency what is about to break. Agencies already know what is about to break. What they lack is hands. So we sell the hands: a fixed price per client project to bring it onto the current version, tested against the vendor's own sandbox, delivered as a merged branch with a written before-and-after note the agency can forward to the client verbatim.

The part that compounds is not the code we write, it is the record of what breaks. After the fifth agency sends us the same Shopify checkout extension or the same Xero payroll call, we already know which twelve lines change and which tests fail first. We keep a private library of migration recipes keyed to the exact vendor version pair, built from real client codebases rather than from documentation. Documentation says what the new version does. Our library says what actually broke in real code and how long it took to fix, which is what lets us quote a fixed price at all. Rivals can copy our price list; they cannot copy the thousand repositories that produced it.

A model does the first pass on each repository and drafts the patch, so a small team can service many projects at once. A senior engineer reviews before anything is delivered. That keeps the margin without putting an unreviewed rewrite into a client's live checkout.

This is technology sold to technology buyers, and it commits to the tech-vertical shape: the ecosystem is the named platform developer programmes, and the thing that hurts is their published version-retirement deadline. The buyer role is the agency owner or technical director who signs subcontractor invoices. The recurring trigger is each vendor's published end-of-support date. The deliverable is a merged, tested branch plus a client-ready note. The public source proving the pain is already paid for is the vendors' own published deprecation calendars, which name the dates that force the work, alongside the fact that agencies already carry subcontract development costs in their accounts filed at Companies House.

We start where the deadlines are hardest and the ecosystem is densest in the UK, which is Shopify and the accounting platforms, then widen one platform at a time as the recipe library fills.
